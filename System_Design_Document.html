System Design Document: Shopify AI Taxonomy Engine

1. Executive Summary

The Shopify AI Taxonomy Engine is a distributed, full-stack application designed to autonomously classify raw e-commerce product data into official Shopify categories. The system utilizes advanced PostgreSQL string searching, a Multi-Agent LLM pipeline (Google Gemini 1.5 Flash), and asynchronous Celery background workers to process massive datasets (10,000+ products) rapidly and accurately, without hallucinating invalid categories.

2. Technology Stack

  • Frontend: React 18 (Vite), Vanilla CSS (Glassmorphism UI)
  • Backend Framework: Django REST Framework (Python)
  • Database: PostgreSQL (with pg_trgm extension for fuzzy searching)
  • Data Processing: Pandas (for variant deduplication)
  • Async Engine: Celery + Redis
  • AI Engine: Google Gemini 1.5 Flash (Multi-Modal Vision + Text)
  • Infrastructure: Docker & Docker Compose

3. Requirements Mapping

# Requirement Architectural Solution
1 Imports the provided product list. The frontend features a Drag & Drop UI that passes the Excel file to the Django API, which uses pandas.read_excel() to parse the rows.
2 Uses Shopify taxonomy to identify category. Implemented a Multi-Agent RAG Pipeline. PostgreSQL pg_trgm retrieves the top 5 official categories, and Agent 1 selects the most accurate one.
3 Detects relevant category attributes and values. Agent 2 dynamically loads the exact required attributes for the chosen category from simplified_taxonomy.json and extracts values via a strict JSON schema prompt.
4 Supports products with and without images. Uses Google Gemini Vision. Celery downloads the image to memory. If an image is missing, the code gracefully falls back to a text-only prompt payload.
5 Handles missing descriptions. The Pandas normalizer handles NaN values safely. The pipeline relies heavily on the normalized_title and product_type to retrieve accurate Trigram matches.
6 Uses title, description, type, brand, and image. All available variables are dynamically injected into a comprehensive product_context string within the Gemini prompt template.
7 Provides a confidence score. Agent 1 returns a float (0.0 to 1.0). If the AI's string perfectly matches the database candidate, the system deterministically overrides confidence to 0.98.
8 Provides alternative suggestions. The top 4 unused RAG candidate strings are saved to a JSONB column (alternative_suggestions) and displayed as clickable buttons in the UI for 1-click manual overrides.
9 Identifies products for manual review. If the final confidence score falls below 80%, the product status is flagged as MANUAL_REVIEW and badged yellow in the Dashboard.
10 Processes in batches (10,000+ products). Pandas groups variants into unique families (80% reduction). Celery/Redis dispatches items to concurrent background workers, executing in parallel without freezing the web server.
11 Handles failures without stopping process. Image requests have a strict 5-second timeout. Gemini 429 errors trigger Celery's exponential backoff/retry. The DB tracks status, allowing instant resume after crashes.
12 Simple interface to view/update results. A modern React Dashboard provides data grids, status filters, and specific "Drill-Down" detail pages where human managers can review and override AI categorizations with a single click.

4. Database Schema (PostgreSQL)

  • Category: id (Primary Key), name (Indexed with pg_trgm), parent (Self-referential).
  • ProductFamily: id, normalized_title, status, predicted_category, confidence_score, extracted_attributes (JSONB), alternative_suggestions (JSONB).
  • Product: sku (Primary Key), family (ForeignKey), title, description, image_url.

5. Scalability & Fault Tolerance

Rate Limiting Protection: Firing 10,000 tasks instantly would result in immediate API bans. The Celery worker is configured to catch 429 ResourceExhausted errors, reads the Google retry_delay header, and utilizes Celery's exponential backoff. This ensures the queue safely pauses and self-heals when throttled.

Catastrophic Crash Recovery: Because the system is stateful, every ProductFamily explicitly commits its state to the database. If a server loses power halfway through a batch of 10,000, all completed items are safely saved. Rebooting cleanly ignores the finished items and instantly resumes execution exactly where it died.
